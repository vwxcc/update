# AI CH: автообновления на ZimaOS

Репозиторий устанавливает и обслуживает обновлятор для приложения из `vwxcc/deepseekw`, ветка `main`. Проверка новых коммитов выполняется systemd-таймером каждые 3 минуты.

## Что исправлено в текущем updater

- Используется фактический контейнер приложения. При повторной установке скрипт ищет запущенный контейнер с файлами `/app/app/main.py`, `/app/frontend/index.html` и `/app/requirements.txt`. Для этой конфигурации имя по умолчанию — `ai-ch-mega`, а не старые `ai-ch` или `chatstudio-v2`.
- Не требуется каталог `sandbox/`. Updater обслуживает только `app/`, `frontend/` и `requirements.txt` из актуального проекта.
- Health-check выполняется внутри выбранного контейнера: `127.0.0.1:8000/api/health`. Он не зависит от того, опубликован ли порт контейнера на хосте как 3050.
- До замены файлов updater сохраняет предыдущие `app/`, `frontend/` и `requirements.txt`. Если новая версия не отвечает, он возвращает их и прежний указатель зависимостей.
- После успешной проверки удаляются исходные файлы из `app/` и `frontend/`, которые были в предыдущей версии, но отсутствуют в новой.
- Контейнер не пересоздаётся. При обновлении не меняются его имя, Docker mounts, переменные окружения, `.env`, база данных, `data/` и `uploads/`.
- Изменившиеся зависимости ставятся в отдельный каталог версии. Предыдущий набор сохраняется для отката.
- Коммит, отклонённый старой версией updater, будет проверен повторно после установки новой версии updater.

## Установка или обновление самого updater

Запусти команды на хосте ZimaOS:

```sh
curl -fsSL https://raw.githubusercontent.com/vwxcc/update/main/install.sh -o /tmp/ai-ch-updater-install.sh
sudo sh /tmp/ai-ch-updater-install.sh
```

Установщик:
1. Переиспользует GitHub token из `/etc/ai-ch-updater.env`, если он уже сохранён.
2. Ищет запущенный контейнер AI CH по структуре каталогов. Если найден `ai-ch-mega`, он будет предложен по умолчанию. Имя можно подтвердить нажатием Enter.
3. Проверяет, что в существующем контейнере есть `/app/app/main.py`, `/app/frontend/index.html` и `/app/requirements.txt`.
4. При повторной установке не создаёт новые каталоги приложения и не переписывает его `.env`, mounts, данные или загрузки.
5. Обновляет файл updater, конфигурацию systemd и включает таймер. После установки запускается одна немедленная проверка.

Для приватного `vwxcc/deepseekw` нужен GitHub fine-grained token с правом **Contents: Read-only** только для этого репозитория. Token вводится скрытым вводом и хранится на хосте в `/etc/ai-ch-updater.env` с правами `600`. Он не передаётся в контейнер приложения и не записывается в URL.

## Параметры текущего сервера

| Параметр | Значение |
|---|---|
| Репозиторий приложения | `vwxcc/deepseekw` |
| Ветка | `main` |
| Контейнер приложения | `ai-ch-mega` |
| Порт внутри контейнера | `8000` |
| Опубликованный порт на хосте | `3050` |
| Health endpoint | `/api/health` |
| Каталог updater | `/DATA/AppData/ai-ch-updater` |
| Конфигурация с GitHub token | `/etc/ai-ch-updater.env` |
| Интервал проверки | 3 минуты |

При переустановке имя контейнера и внешний порт считываются из работающего Docker-контейнера там, где это возможно. Вопрос установщика позволяет подтвердить или изменить выбранное имя. У уже существующего контейнера порт публикации не меняется.

## Как проходит обновление

1. Updater получает SHA последнего коммита приватного GitHub-репозитория через API.
2. Скачивает архив этого конкретного SHA. При перенаправлении на `codeload.github.com` GitHub token не передаётся.
3. Проверяет структуру релиза: `app/main.py`, `frontend/index.html`, непустой `requirements.txt`, синтаксис всех Python-файлов в `app/`.
4. Сохраняет резервную копию текущего кода и файла зависимостей.
5. Загружает новые файлы во временный каталог внутри контейнера. Если изменился `requirements.txt`, подготавливает отдельный набор зависимостей, не заменяя рабочий.
6. До остановки сайта выполняет предварительный импорт приложения и запускает FastAPI lifespan в изолированной временной рабочей папке с очищенным окружением. SQLite для этой проверки создаётся во временном каталоге, а не в `/app/data`.
7. Только после успешной предварительной проверки останавливает выбранный контейнер, заменяет код и запускает его снова.
8. Проверяет ответ `/api/health` изнутри контейнера на порту 8000.
9. При неудаче возвращает предыдущие файлы и зависимости, удаляет файлы, добавленные отвергнутой версией, запускает старую версию и повторяет health-check.
10. Только после успешной проверки помечает SHA как применённый и очищает старые релизы и резервные копии сверх установленного лимита.

Обновлятор не выполняет миграции базы данных автоматически. Изменения схемы БД должны быть совместимы с уже существующими данными либо иметь отдельный безопасный сценарий миграции.

## Где хранятся файлы

- Код updater: `/DATA/AppData/ai-ch-updater/auto_deploy_daemon.py`
- Состояние обновлений: `/DATA/AppData/ai-ch-updater/state.json`
- Резервные копии кода: `/DATA/AppData/ai-ch-updater/backups/`
- Скачанные релизы: `/DATA/AppData/ai-ch-updater/releases/`
- Лог updater: `/DATA/AppData/ai-ch-updater/logs/updater.log`
- Секрет GitHub: `/etc/ai-ch-updater.env` (права `600`)
- systemd service: `/etc/systemd/system/ai-ch-updater.service`
- systemd timer: `/etc/systemd/system/ai-ch-updater.timer`
- восстановление после перезагрузки: `/etc/systemd/system/ai-ch-recovery.service`

## Проверка работы

```sh
systemctl status ai-ch-updater.timer --no-pager
systemctl list-timers ai-ch-updater.timer
systemctl status ai-ch-updater.service --no-pager
journalctl -u ai-ch-updater.service -n 100 --no-pager
tail -n 100 /DATA/AppData/ai-ch-updater/logs/updater.log
docker ps --filter name=ai-ch-mega
docker logs --tail 100 ai-ch-mega
```

Запустить проверку вручную:

```sh
sudo systemctl start ai-ch-updater.service
```

Проверка health endpoint непосредственно из контейнера:

```sh
docker exec ai-ch-mega python -c "import urllib.request; print(urllib.request.urlopen('http://127.0.0.1:8000/api/health', timeout=5).read().decode())"
```

Остановить автоматические проверки:

```sh
sudo systemctl disable --now ai-ch-updater.timer
```

## Ограничения и безопасность

- Требуются root, Docker CLI, curl, tar, Python 3 и systemd на хосте ZimaOS.
- Установщик не подключается к ZimaOS удалённо: команды нужно выполнить в его терминале.
- Код обновляется внутри существующего контейнера без сборки Docker-образа и без его пересоздания. Если ZimaOS удалит контейнер и создаст его заново из исходного образа, файлы, скопированные в writable layer, могут пропасть.
- Health-check подтверждает только доступность endpoint. Он не проверяет все AI-провайдеры, регистрацию, работу каждой функции или совместимость миграций БД.
- База данных, пользовательские файлы и `.env` не входят в резервную копию updater и не изменяются им.
- Доступ к Docker эквивалентен широким правам на хост. Не публикуй `.env`, GitHub token или файлы конфигурации с секретами.
